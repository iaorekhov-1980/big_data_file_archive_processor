## **Промпт для разработки ODS-модуля (сканирование, дедупликация, очистка)**

### **1. Общая информация**
Проект: автоматизация обработки домашнего файлового архива в Yandex Cloud.  
Текущая задача: реализовать модуль для работы с ODS-слоем (сырые данные) на Yandex Disk.  
Цель: при загрузке нового источника (папки в `/ods/`) выполнить:
- сканирование всех файлов источника с получением метаданных и MD5-хеша через API Yandex Disk;
- идентификацию глобальных дубликатов (по хешу) и маркировку их в базе данных;
- последующее физическое удаление дубликатов из источника;
- рекурсивное удаление пустых папок, оставшихся после удаления файлов.

Все операции запускаются вручную (поэтапно) через Cloud Functions с HTTP-триггерами.  
Метаданные хранятся в **Yandex Database (YDB)**.  
Код пишется на **Go**, инфраструктура описывается в **Terraform**.

### **2. Детальные требования**

#### **2.1. Структура таблиц в YDB**

```sql
-- Таблица уникальных файлов (глобальный каталог)
CREATE TABLE files (
    hash Utf8,           -- MD5 хеш (как возвращает API Яндекса)
    size Uint64,
    mime_type Utf8,
    created_at Timestamp,
    updated_at Timestamp,
    PRIMARY KEY (hash)
);

-- Таблица всех путей файлов (активных и удалённых)
CREATE TABLE file_paths (
    path Utf8,           -- полный путь в ODS, например /ods/2025-03-20_phone/photo.jpg
    source_id Utf8,      -- имя папки источника (например, "2025-03-20_phone")
    hash Utf8,           -- ссылка на files.hash
    is_active Bool,      -- true = файл физически присутствует на диске и является уникальным (не дубликат)
    deleted_at Timestamp?, -- когда файл был удалён физически (если is_active=false и удалён)
    created_at Timestamp,
    updated_at Timestamp,
    PRIMARY KEY (path)
) WITH (
    INDEX hash_idx GLOBAL ON (hash)
);

-- Таблица мониторинга обработки источников
CREATE TABLE source_processing (
    source_id Utf8,      -- имя папки источника
    -- Этап сканирования
    scan_started_at Timestamp?,
    scan_completed_at Timestamp?,
    current_offset Uint64?,        -- для возобновления сканирования
    total_files_found Uint64?,
    scan_status Utf8?,             -- in_progress, completed, failed
    scan_error Utf8?,
    -- Этап удаления дубликатов
    processing_started_at Timestamp?,
    processing_completed_at Timestamp?,
    files_processed Uint64?,       -- сколько файлов обработано (из помеченных на удаление)
    files_deleted Uint64?,         -- сколько реально удалено
    processing_status Utf8?,
    processing_error Utf8?,
    -- Этап очистки пустых папок
    cleanup_started_at Timestamp?,
    cleanup_completed_at Timestamp?,
    folders_deleted Uint64?,
    cleanup_status Utf8?,
    cleanup_error Utf8?,
    -- Служебные поля
    created_at Timestamp,
    updated_at Timestamp,
    PRIMARY KEY (source_id)
);
```

#### **2.2. Взаимодействие с Yandex Disk API**

- **Базовый URL:** `https://cloud-api.yandex.net/v1/disk/`
- **Авторизация:** OAuth-токен (хранить в Yandex Lockbox, функция получает через SDK).
- **Получение списка файлов в папке (рекурсивно, плоский список):**
  ```
  GET /resources/files?path=/ods/{source_id}&limit=100&offset={offset}
  ```
  Ответ содержит массив `items` с полями: `path`, `md5`, `size`, `mime_type`, `created`, `modified`.  
  Пагинация: пока длина `items` равна `limit`, есть следующие страницы.
- **Удаление файла:**
  ```
  DELETE /resources?path={path}&permanently=true
  ```
  Успешный ответ: `204 No Content`.
- **Проверка содержимого папки (для очистки пустых):**
  ```
  GET /resources?path={folder_path}
  ```
  В ответе `_embedded.items` содержит список файлов и подпапок.

**Важно:** соблюдать лимиты API (не более 40 запросов в секунду). Добавлять задержки между запросами.

#### **2.3. Функция `scan_source` (HTTP-триггер)**

- **Входные параметры** (JSON):
  ```json
  {
    "source_id": "2025-03-20_phone",
    "resume_offset": 0   // опционально, для продолжения прерванного сканирования
  }
  ```
- **Логика:**
  1. Проверить запись в `source_processing` для данного `source_id`. Если нет – создать с `scan_status = 'in_progress'`, `scan_started_at = now()`, `current_offset = resume_offset`. Если есть и статус `completed` – можно либо вернуть ошибку, либо перезапустить (обнулив offset).
  2. В цикле, пока не будет получена последняя страница:
     - Вызвать API Yandex Disk для получения файлов.
     - Для каждого файла:
       - Проверить наличие `hash` в таблице `files` (запрос `SELECT hash FROM files WHERE hash = $md5`).
       - Если хеш **не найден**:
         - Вставить в `files` (hash, size, mime_type, created_at = now()).
         - Вставить в `file_paths` (path, source_id, hash, is_active = true, created_at = now()).
       - Если хеш **найден**:
         - Вставить в `file_paths` (path, source_id, hash, is_active = false, created_at = now()).
         - (files не трогать)
     - После обработки страницы обновить `source_processing`: увеличить `current_offset` на количество обработанных файлов, установить `updated_at`.
  3. Когда количество полученных файлов на странице меньше `limit`, сканирование завершено:
     - Обновить `scan_completed_at = now()`, `scan_status = 'completed'`, `total_files_found = current_offset`.
  4. При ошибке (сеть, API, таймаут) записать `scan_error` и установить `scan_status = 'failed'`. Функция должна завершиться, но offset сохранится для возобновления.
- **Идемпотентность:** повторный запуск с тем же offset не должен создавать дубликаты записей. Для этого перед вставкой в `file_paths` можно проверять наличие `path`, но по условию каждый файл уникален по пути, так что повторная отправка того же пути приведёт к конфликту первичного ключа. Лучше предусмотреть `UPSERT` с игнорированием или проверку через `SELECT` перед вставкой.

#### **2.4. Функция `cleanup_duplicates` (HTTP-триггер)**

- **Входные параметры:**
  ```json
  { "source_id": "2025-03-20_phone" }
  ```
- **Предусловие:** сканирование для этого источника должно быть завершено (`scan_status = 'completed'`). Иначе вернуть ошибку.
- **Логика:**
  1. Обновить `source_processing`: `processing_started_at = now()`, `processing_status = 'in_progress'`, сбросить счётчики.
  2. Выбрать из `file_paths` все записи для данного источника, где `is_active = false` и `deleted_at IS NULL` (т.е. помеченные как дубликаты и ещё не удалённые).
  3. Для каждой такой записи:
     - Вызвать API Yandex Disk для удаления файла по `path`.
     - При успехе (`204`) обновить запись в `file_paths`: установить `deleted_at = now()`, `updated_at = now()`.
     - При ошибке (например, 404 — файл уже не существует) можно считать, что файл уже удалён, и тоже обновить `deleted_at` (логировать предупреждение).
     - Увеличить счётчики `files_processed` и `files_deleted` (последний только при успехе или 404).
     - Добавить небольшую задержку (например, 50-100 мс) между вызовами, чтобы не превысить лимиты API.
  4. После обработки всех записей обновить `processing_completed_at = now()`, `processing_status = 'completed'`, `files_processed`, `files_deleted`.
  5. В случае ошибки на каком-то файле (например, 500) – записать в `processing_error`, установить статус `failed` и прерваться. При повторном запуске функция должна продолжить с того места, где остановилась (можно использовать маркер последнего обработанного пути, но для простоты можно повторно обрабатывать все записи с `is_active=false` и `deleted_at IS NULL` – идемпотентность обеспечивается проверкой `deleted_at`).

#### **2.5. Функция `cleanup_folders` (HTTP-триггер)**

- **Входные параметры:**
  ```json
  { "source_id": "2025-03-20_phone" }
  ```
- **Предусловие:** этап удаления дубликатов для источника завершён (опционально, но логично).
- **Логика:**
  1. Обновить `source_processing`: `cleanup_started_at = now()`, `cleanup_status = 'in_progress'`.
  2. Получить список всех уникальных путей папок в источнике. Можно извлечь из `file_paths` для данного источника (выделить директории из `path`) или получить через API, перечислив содержимое папки `/ods/{source_id}` рекурсивно (но это повторный обход). Предпочтительнее использовать данные из `file_paths`, так как они уже есть. Однако нужно учитывать, что после удаления файлов некоторые папки могли полностью опустеть, и их нет в `file_paths`. Поэтому надёжнее использовать API для актуального состояния.
   - Альтернатива: после удаления файлов сделать запрос к API для получения структуры папок (список всех папок, даже пустых). Для этого можно использовать `GET /resources?path=/ods/{source_id}&limit=1000` и рекурсивно обойти все папки, но это может быть много запросов. Для упрощения можно сначала собрать все пути папок из `file_paths` (включая родительские), а затем проверить через API только те, которые могут быть пустыми.
   - Рекомендуемый подход:
     - Собрать множество всех директорий, встречающихся в путях файлов источника (например, для каждого пути выделять все префиксы). Это даст все папки, в которых когда-то были файлы.
     - Отсортировать их по убыванию глубины.
     - Для каждой папки выполнить запрос к API `GET /resources?path={folder_path}` и проверить `_embedded.items`: если массив пуст, значит папка пуста, и её можно удалить.
     - После удаления папки проверить родительскую рекурсивно.
  3. Для каждой удаляемой папки:
     - Вызвать API `DELETE /resources?path={folder_path}&permanently=true`.
     - Увеличить счётчик `folders_deleted`.
  4. Обновить `cleanup_completed_at`, `cleanup_status = 'completed'`, `folders_deleted`.

#### **2.6. Требования к реализации**

- **Язык:** Go 1.21+.
- **Структура проекта:**
  ```
  /cmd
    /scan_source      // main для функции scan_source
    /cleanup_duplicates
    /cleanup_folders
  /internal
    /ydb              // работа с YDB (инициализация, запросы)
    /disk             // клиент для Yandex Disk API
    /models           // структуры данных
    /config           // загрузка конфигурации из environment
  /terraform          // файлы .tf для создания инфраструктуры
  ```
- **Обработка ошибок:** все функции должны логировать ошибки (через `log.Printf` или `fmt.Fprintf` в stderr). В случае временных сбоев (5xx от API) – повторять с экспоненциальной задержкой (до 3 раз).
- **Конфигурация:** через переменные окружения: `YDB_ENDPOINT`, `YDB_DATABASE`, `IAM_TOKEN_URL` (для получения токена из метаданных), `LOCKBOX_SECRET_ID` (где хранится OAuth-токен Яндекса). В Cloud Functions эти переменные задаются при создании.
- **Логирование:** в stdout (собирается Yandex Cloud Logging). Для каждого важного шага выводить информационные сообщения: начало/конец обработки, количество файлов, ошибки.
- **Таймауты:** функции должны учитывать максимальное время выполнения Cloud Functions (10 минут). При необходимости разбивать обработку на несколько вызовов (но в рамках данного задания считаем, что объём источника укладывается в лимит).

#### **2.7. Terraform-артефакты**

Необходимо создать Terraform-конфигурацию для развёртывания:
- Трёх Cloud Functions (`scan_source`, `cleanup_duplicates`, `cleanup_folders`) с соответствующими триггерами (HTTP).
- YDB-базы и таблиц (описаны выше).
- Сервисного аккаунта с ролями:
  - `ydb.editor` – для работы с YDB.
  - `lockbox.payloadViewer` – для доступа к секрету с OAuth-токеном.
  - `functions.functionInvoker` – для вызова функций (если потребуется).
- Lockbox-секрета, в котором будет сохранён OAuth-токен пользователя (значение ввести вручную после создания).
- Настроек окружения для функций (переменные `YDB_ENDPOINT`, `YDB_DATABASE`, `LOCKBOX_SECRET_ID` и т.д.).

Также нужен выходной URL для каждой функции, чтобы можно было их вызывать вручную (например, через curl).
