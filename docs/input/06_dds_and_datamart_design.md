**Промпт для нового чата: проектирование DDS и Data Mart**

Привет! Мы продолжаем разработку системы для управления домашним файловым архивом на базе Yandex Cloud. Ранее мы спроектировали и частично реализовали модуль для работы с **ODS-слоем** (сырые данные). Теперь необходимо перейти к проектированию следующих уровней: **DDS** (deduplicated data store) и **Data Mart** (витрина для медиафайлов).

### Что уже сделано (контекст)
- Источники (папки) вручную загружаются в Yandex Disk по пути `/ods/DD_MM_YYYY_source`.
- Реализованы Cloud Functions на Go для:
  - **Сканирования источника** – получение списка файлов через API Yandex Disk, проверка глобального хеша (MD5), заполнение таблиц `files` (уникальные файлы) и `file_paths` (все пути с флагами `is_active`). Дубликаты помечаются `is_active = false`.
  - **Очистки дубликатов** – физическое удаление файлов, помеченных как неактивные, и обновление `deleted_at`.
  - **Очистки пустых папок** – рекурсивное удаление пустых каталогов после удаления файлов.
- Таблицы в YDB: `files`, `file_paths`, `source_processing` (мониторинг обработки источников).

### Теперь нужно спроектировать два слоя:

#### 1. DDS (слой уникальных файлов)
**Цель:** физически хранить только один экземпляр каждого уникального файла (по хешу), независимо от того, в скольких источниках он встречался. Это позволит экономить место и создать единую базу файлов для дальнейшего использования.

**Вопросы для обсуждения:**
- **Организация хранения на Yandex Disk:**  
  Предлагаю использовать структуру `/dds/<первые два символа хеша>/<следующие два>/<полный хеш>`. Например: `/dds/ab/cd/abcdef123456...`. Это стандартный подход для S3-подобных хранилищ, чтобы избежать слишком большого количества файлов в одной папке. Поддерживает ли Yandex Disk такое? Да, он позволяет создавать вложенные папки.
- **Когда копировать файл в DDS?**  
  Варианты:
  - Сразу при обнаружении нового уникального файла в процессе сканирования (после вставки в `files`). Тогда мы вызываем API копирования внутри Yandex Disk из `/ods/...` в `/dds/...`. Это удобно, но может замедлить сканирование.
  - Отдельным этапом после завершения сканирования источника (аналогично очистке). Тогда выбираем из `file_paths` все записи для источника с `is_active = true` (уникальные файлы) и копируем их.
  - Комбинированный подход: копировать сразу, но асинхронно через очередь. Однако для pet-проекта можно выбрать что-то простое.
- **Обновление таблиц:**  
  В таблице `files` нужно хранить путь к DDS (`dds_path`). После успешного копирования обновляем это поле.
- **Обработка ситуации, когда файл уже есть в DDS (из другого источника):**  
  Не копируем повторно, только добавляем запись в `file_paths` (как мы уже делаем). Но для DDS сам файл уже существует, поэтому ничего делать не нужно.
- **Необходимость удаления файлов из DDS:**  
  Если файл больше не встречается ни в одном активном источнике (все `is_active = false`), теоретически его можно удалить из DDS. Но для упрощения пока не будем это реализовывать – оставим как бессрочное хранилище.

#### 2. Data Mart (витрина для медиафайлов)
**Цель:** предоставить удобный доступ к фото и видео, сгруппированным по годам и месяцам съёмки. Это нужно для просмотра архива в хронологическом порядке.

**Ключевые моменты:**
- **Определение даты съёмки:**  
  - Для фото – из EXIF (тег `DateTimeOriginal`).  
  - Для видео – из метаданных контейнера (например, `com.apple.quicktime.creationdate` или `creation_time` в MP4). Можно использовать библиотеки типа `go-exif` и `goav`/`ffprobe`.
  - Если дата не извлекается, можно использовать дату модификации файла (из API Yandex Disk) или дату загрузки.
- **Организация хранения на диске:**  
  Нужно создать структуру папок `/datamart/YYYY/MM/`, внутри которой будут находиться файлы (или ссылки на них).  
  **Варианты:**
  1. **Физическое копирование** – копируем файл из DDS в соответствующую папку по году/месяцу. Это просто и понятно, но занимает дополнительное место (фактически ещё одна копия каждого медиафайла). При 2 ТБ уникальных файлов витрина может занять столько же.
  2. **Zero-byte объекты с метаданными** – создаём в папке `/datamart/...` пустые файлы с тем же именем, но в метаданных (или в отдельной таблице) храним ссылку на реальный файл в DDS. При просмотре через веб-интерфейс мы можем подменять запрос и отдавать файл из DDS. Yandex Disk не поддерживает символические ссылки, но мы можем использовать API-шлюз или собственное приложение.
  3. **Логическая витрина через таблицу** – не создаём физические папки, а храним соответствие `(год, месяц, список хешей)` в отдельной таблице YDB, а для просмотра используем простое веб-приложение, которое динамически строит структуру папок и отдаёт файлы по запросу. Это наиболее гибко и не занимает места, но требует разработки интерфейса.
- **Когда и как строить витрину:**  
  - После того как файлы скопированы в DDS и для них извлечена дата съёмки, можно запускать процесс построения витрины. Он может быть отдельной функцией, которая обрабатывает все медиафайлы, у которых ещё нет `datamart_path` (или записи в витрине).
  - Витрина должна обновляться при добавлении новых источников или при изменении даты съёмки (если мы её пересчитываем).
- **Какие поля добавить в таблицы:**  
  - В `files`: `date_taken Timestamp?` (извлечённая дата съёмки), `datamart_path Utf8?` (если выбрано физическое копирование).
  - Возможно, отдельная таблица `media_mart` с полями: `year Uint16`, `month Uint8`, `hash Utf8`, `file_name Utf8` – для логической витрины.
