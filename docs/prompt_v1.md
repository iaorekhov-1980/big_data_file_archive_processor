## 🚀 **Проект: Управление домашним файловым архивом на Yandex Disk с дедупликацией и метаданными в YDB**

### **1. Общие цели**
- Собрать разрозненные файлы со старых ноутбуков, внешних дисков, карт памяти в единое облачное хранилище **Yandex Disk** (2 ТБ).
- Провести дедупликацию: физически хранить только уникальные файлы (DDS-слой), но сохранять информацию обо всех исходных путях (ODS-слой).
- Создать витрину для медиафайлов (фото, видео), сгруппированную по годам и месяцам на основе даты съёмки (Data Mart).
- Реализовать процедуру очистки ODS-слоя по фильтрам (типы файлов, папки) с сохранением метаданных и возможностью последующего опознавания повторно появившихся файлов (без повторной загрузки в DDS).

### **2. Роли слоёв на Yandex Disk**
- **ODS** (raw data): папка `/ods/<source_name>/...` – исходные файлы, загруженные вручную.
- **DDS** (deduplicated): папка `/dds/<hash[:2]>/<hash[2:4]>/<hash>` – физически уникальные файлы.
- **Data Mart**: папка `/datamart/<год>/<месяц>/` – копии медиафайлов (или ссылки) для удобного просмотра.

### **3. Компоненты в Yandex Cloud**
| Сервис | Назначение |
|--------|------------|
| **Yandex Database (YDB)** | Хранение метаинформации о файлах (хеш, все пути, дата съёмки, размер, тип). |
| **Yandex Message Queue** | Очереди для асинхронной обработки: `process-file`, `copy-to-dds`, `cleanup-tasks`. |
| **Yandex Cloud Functions** | Безсерверные обработчики: сканер ODS, воркер дедупликации, копировщик в DDS, построитель витрины, очиститель ODS. |
| **Yandex Lockbox** | Хранение OAuth-токена для доступа к Yandex Disk. |
| **Yandex Monitoring / Logging** | Мониторинг и отладка. |

### **4. Схема данных в YDB**
```sql
CREATE TABLE files (
    hash String,          -- SHA256 hex
    size Uint64,
    mime_type String,
    date_taken Timestamp?,-- из EXIF/метаданных видео
    ods_paths List<String>, -- все пути в ODS (включая удалённые? лучше хранить только актуальные, а для удалённых иметь флаг)
    dds_path String?,        -- путь в DDS (если файл уникален и скопирован)
    datamart_path String?,   -- путь в Data Mart (если скопирован)
    is_deleted Bool,         -- помечен ли как удалённый из ODS (но метаданные сохраняются)
    created_at Timestamp,
    updated_at Timestamp,
    PRIMARY KEY (hash)
);

-- Для быстрого поиска по пути ODS (например, при повторном сканировании) можно создать индекс:
CREATE TABLE ods_path_index (
    path String,         -- полный путь в ODS (например, /ods/laptop/photo.jpg)
    hash String,         -- ссылка на files
    PRIMARY KEY (path)
);
```

### **5. Обработка файлов (поток)**

#### **5.1 Сканирование ODS (функция `scanner`)**
- Запускается вручную (HTTP) или по расписанию.
- Получает через [REST API Yandex Disk](https://yandex.ru/dev/disk/api/reference/all-files.html) рекурсивный список файлов в `/ods`.
- Для каждого найденного файла отправляет сообщение в очередь `process-file` с параметрами:
  ```json
  { "path": "/ods/source/...", "etag": "...", "size": 12345 }
  ```

#### **5.2 Воркер дедупликации (функция `worker`)**
- Триггер: очередь `process-file`.
- Читает файл из Yandex Disk через **WebDAV** (потоково), вычисляет SHA256.
- Проверяет наличие хеша в таблице `files`:
  - **Новый хеш**: создаёт запись в `files`, заполняет `ods_paths` = [path], `size`, `mime_type`. Если файл медиа (расширение .jpg, .mp4 и т.д.) – пытается извлечь дату съёмки (EXIF для фото, ffprobe для видео) и заполняет `date_taken`. Отправляет сообщение в очередь `copy-to-dds` (содержит хеш и путь в ODS).
  - **Существующий хеш**: добавляет текущий `path` в `ods_paths` (если его там нет). Если `is_deleted` был true – сбрасывает в false? (обсудить). Файл уже есть в DDS, поэтому повторно не копируем.
- Обновляет индекс `ods_path_index`: вставляет запись `(path, hash)`.

#### **5.3 Копирование в DDS (функция `copier-to-dds`)**
- Триггер: очередь `copy-to-dds` (сообщение: `{"hash": "...", "ods_path": "..."}`).
- Проверяет, что `dds_path` ещё не заполнен (на случай повторной отправки).
- Генерирует целевой путь: `/dds/<hash[:2]>/<hash[2:4]>/<hash>`.
- Выполняет [копирование внутри Yandex Disk](https://yandex.ru/dev/disk/api/reference/copy.html) из `ods_path` в `dds_path`.
- После успеха обновляет запись в `files`: `dds_path = целевой путь`.

#### **5.4 Построитель витрины (функция `mart-builder`)**
- Запускается по расписанию (например, раз в сутки) или после копирования в DDS.
- Делает запрос к YDB: выбрать все записи, у которых `date_taken IS NOT NULL` и `datamart_path IS NULL` (ещё не обработаны).
- Группирует по году/месяцу.
- Для каждой группы:
  - Создаёт папку `/datamart/YYYY/MM` через API `mkdir` (если не существует).
  - Для каждого файла копирует из `dds_path` в `/datamart/YYYY/MM/<original_filename>` (при совпадении имён можно добавить хеш).
  - Обновляет `datamart_path` в записи.

#### **5.5 Очистка ODS (функция `cleanup-ods`)**
- Запускается вручную с параметрами фильтрации (JSON):
  ```json
  {
    "prefix": "/ods/old_laptop/",       // только файлы в этой папке
    "extensions": [".tmp", ".bak"],     // или по расширениям
    "older_than": "2023-01-01",         // по дате модификации (API Yandex Disk даёт last_modified)
    "types": ["image", "video"]         // или по mime-типу (но придётся сначала получить метаданные)
  }
  ```
- Алгоритм:
  1. Получить список файлов в ODS, соответствующих фильтрам (используя API Disk или индексы YDB).
  2. Для каждого файла:
     - Найти хеш через индекс `ods_path_index`.
     - Удалить файл из Yandex Disk (через API `delete`).
     - Удалить соответствующую запись из `ods_path_index`.
     - Обновить запись в `files`: удалить этот путь из `ods_paths`. Если после удаления `ods_paths` стал пустым и файл не скопирован в DDS? Но по логике, если файл уникальный и был в DDS, то `ods_paths` может быть пуст, но `dds_path` существует – такой случай возможен? Нет, если файл уникальный, он всегда имеет хотя бы один ODS-путь (тот, из которого скопирован). Если удалить последний ODS-путь, то у нас останется файл в DDS, но без привязки к источнику. Это допустимо? Возможно, стоит пометить запись как `orphaned` или удалить и из DDS (но осторожно, т.к. могут быть ссылки из Data Mart). Лучше оставить: файл в DDS остаётся, но без активных ODS-путей. При последующем появлении такого же файла (с таким хешем) мы добавим новый ODS-путь, и файл не будет копироваться повторно.
  3. Логировать результаты.

### **6. Повторное появление удалённого файла**
- Если после очистки тот же файл снова загружается в ODS (вручную или из другого источника), воркер `worker`:
  - Вычислит хеш, найдёт запись в `files`.
  - Добавит новый путь в `ods_paths` и в индекс.
  - Так как `dds_path` уже существует, файл не будет скопирован повторно.
  - Если файл медиа, его дата съёмки уже известна, поэтому при следующем запуске `mart-builder` он может быть добавлен в витрину (если ещё не был).

### **7. Технологический стек**
- **Язык**: Go (для всех функций, так как отличная поддержка конкурентности, библиотеки для YDB, HTTP-клиенты).
- **Инфраструктура как код**: Terraform (провайдер Yandex Cloud).
- **Среда разработки**: VS Code с плагином Continue + DeepSeek API (агентное программирование).

- Обработка ошибок, повторные попытки, идемпотентность.

### **9. Ожидаемый результат**
Рабочая система, которая:
- Автоматически обрабатывает файлы, загруженные в `/ods` на Yandex Disk.
- Ведёт базу уникальных файлов в YDB.
- Создаёт дедуплицированную копию в `/dds`.
- Строит медиа-витрину по датам в `/datamart`.
- Позволяет выборочно очищать ODS с сохранением метаданных.
